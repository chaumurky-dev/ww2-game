# Deploying Wartide

## Local sandbox

Prereqs: Docker (colima ok), `just`, Rust + `wasm32-unknown-unknown`, `trunk`, `sqlx-cli` (optional;
the server runs its own migrations at startup).

```
just db-up      # Postgres 16 (localhost:5432, wartide/wartide/wartide) + Mailpit (SMTP 1025, UI http://localhost:8025)
just dev        # server on :8080 and `trunk serve` (proxies /api and /ws to the server)
scripts/dev-smoke.sh   # waits for http://localhost:8080/healthz, prints OK
just lint | just test | just psql | just reset-db
```

Defaults for `DATABASE_URL`, `BASE_URL`, `SMTP_*`, `SESSION_SECRET`, `WEB_DIST_DIR` are baked into the
justfile; override them in a `.env` file. Verification emails land in Mailpit.

### Containerised run (verified)

```
just build-image                  # docker build -t wartide:local .  (needs BuildKit/buildx: cache mounts)
just app-up                       # docker compose --profile app up -d --build --wait
just smoke                        # waits for /healthz, prints OK
open http://localhost:8080        # SPA; verification mail appears in Mailpit http://localhost:8025
just app-down                     # stop the app, leave Postgres/Mailpit running
```

The compose `app` service sets `COOKIE_SECURE=false` (the server defaults to secure cookies, which browsers
drop over plain http), `SMTP_HOST=mailpit` and `DATABASE_URL` pointing at the `postgres` service.
The image is multi-stage: `rust:1-bookworm` builds the server and the SPA (trunk downloads the wasm-opt release
pinned in `crates/web/Trunk.toml`; never use the distro `binaryen` package, see that file); the runtime stage is `debian:bookworm-slim`, runs as uid 10001 (non-root) and serves the SPA from
`/app/dist`. Image: about 118 MB of layers
(debian-slim 85 MB, ca-certificates 10 MB, server binary 18 MB, SPA 6 MB; `docker images` may show a larger
number on colima because of the containerd image store). Cold build about 12 min on an x86_64 colima VM, about
2 min with a warm cache.

Verified flow (`scripts/dev-smoke.sh --full`, or `just smoke-full`): register, read the verification mail from
Mailpit, verify, log in, create a private game vs 4 bots, then play USSR's turn by ending phases; the bots
(seat 1-4) then made about 20 actions in the first 10 s. Bots stall only when they need a decision from the human
(e.g. choosing casualties when USSR defends). Notes:

- Colima: `docker build` needs BuildKit (cache mounts). If the macOS docker CLI has no buildx plugin, build
  inside the VM: `colima ssh -- sh -c 'cd $PWD && docker buildx build --load -t wartide:local .'`.
- If port 8080 is taken (for example by `just dev`), run the container on another port:
  `APP_PORT=18080 docker compose --profile app up -d --wait app` (BASE_URL follows APP_PORT).
- Bot commentary is posted to the team chat channel, so `GET /chat?channel=all` is normally empty.

## Architecture on AWS

One ECS Fargate Spot task (0.25 vCPU / 0.5 GB) runs the container, which serves API, WebSocket and SPA, behind an
ALB (HTTP redirects to HTTPS, ACM cert via DNS). RDS Postgres 16 (`db.t4g.micro`) sits in private subnets
and accepts traffic only from the ECS security group. Secrets (DATABASE_URL, SESSION_SECRET, SMTP creds)
live in Secrets Manager and are injected by ECS. Email goes through SES SMTP.

Cost tradeoff: there is no NAT gateway. Tasks run in public subnets with public IPs (inbound locked to the
ALB security group) so they can reach ECR, Secrets Manager, SES and CloudWatch. Move tasks to private subnets
and add a NAT or VPC endpoints if you want stricter isolation.

## 1. Principles

- No secrets in git. Runtime secrets live in Secrets Manager (generated by Terraform); `backend.hcl` and
  `terraform.tfvars` are gitignored.
- GitHub Actions authenticates to AWS with OIDC only (role `wartide-prod-deploy`, trusts
  `github_oidc_subjects`: the `main` ref and the `production` environment, matched with `StringEquals`, plus the
  `aud` condition); no long-lived AWS keys in GitHub.
- Terraform state is private: S3 bucket, versioned, AES256, public access blocked, native S3 locking.
- Everything after bootstrap goes through GitHub Actions (images are built and pushed only by
  `.github/workflows/deploy.yml`; infra changes via Terraform with the `wartide` profile).
- The only manual, non-scripted steps: (a) creating the admin-level principal that runs the bootstrap,
  (b) the NS delegation of `ww2` at the parent zone (hosted at DreamHost; GoDaddy is only the registrar), (c) the SES production-access request.
- Terraform runs as role `wartide-terraform` (least privilege, `infra/iam/wartide-terraform-policy.json`), never as admin.

## 2. Bootstrap runbook

Target: `ww2.chaumurky.net` (registrar GoDaddy; parent zone DNS hosted at DreamHost, see `dig NS chaumurky.net`), us-east-1. Needs Terraform >= 1.10, AWS CLI, `gh`, Docker.
All AWS steps are in `scripts/aws-bootstrap.sh` (idempotent; prints every mutating command; `--yes` skips prompts;
`scripts/aws-bootstrap.sh all [src-profile] [region]` runs the sequence with pauses).

```
# a. Operator role (as the admin profile; ADMIN_PRINCIPAL_ARN defaults to the caller)
AWS_PROFILE=default ADMIN_PRINCIPAL_ARN=arn:aws:iam::<acct>:user/<admin> scripts/aws-bootstrap.sh operator-role
# b. CLI profile 'wartide' (assumes the role)
scripts/aws-bootstrap.sh profile default us-east-1
# c. State bucket
AWS_PROFILE=wartide scripts/aws-bootstrap.sh state-bucket

# d. Terraform: hosted zone + ECR first
export AWS_PROFILE=wartide
cd infra/terraform
cp backend.hcl.example backend.hcl && cp terraform.tfvars.example terraform.tfvars
terraform init -backend-config=backend.hcl
terraform apply -target=aws_route53_zone.main -target=aws_ecr_repository.app
terraform output route53_name_servers

# e. MANUAL at DreamHost (DNS host of chaumurky.net): four NS records, host `ww2`, one per name server. Wait for:
dig NS ww2.chaumurky.net +short

# f. First image (so ECS has one before the first full apply); later images come only from CI
ECR=$(terraform output -raw ecr_repository_url)
aws ecr get-login-password | docker login --username AWS --password-stdin "${ECR%%/*}"
docker buildx build --platform linux/amd64 -t "$ECR:latest" -t "$ECR:$(git rev-parse --short HEAD)" --push ../..
#   (colima without the buildx plugin: run the build via `colima ssh -- docker buildx build ...`)

# g. Everything else (ACM validation, SES records, ALB alias)
terraform apply

# h. GitHub secret + variables from terraform outputs
cd ../.. && scripts/aws-bootstrap.sh github infra/terraform
```

Then run the Deploy workflow and request SES production access in the console (sandbox only sends to verified
addresses). Do not run the full apply before the NS delegation answers: ACM validation would hang. If the account
lacks the GitHub OIDC provider set `create_github_oidc_provider = true`. With an existing zone use
`create_route53_zone = false` and `route53_zone_id`.

Updating the IAM policy later: edit `infra/iam/wartide-terraform-policy.json` (or `wartide-boundary-policy.json`),
re-run `operator-role` as admin (publishes a new default version only if changed; deletes the oldest non-default
version to respect IAM's limit of 5). See `infra/iam/README.md`. The state bucket settings (TLS-only policy, bucket
owner enforced, 90-day noncurrent-version expiry) are re-applied by re-running `scripts/aws-bootstrap.sh state-bucket`.

### Hardening rollout (admin runbook, in this order)

1. As admin: `AWS_PROFILE=default scripts/aws-bootstrap.sh operator-role`. Creates the `wartide-boundary` policy,
   publishes the new `wartide-terraform` version (budgets, ce, guardduty, sns, cloudwatch, account contacts, boundary
   conditions, protective denies) and attaches the boundary to the existing `wartide-prod-*` roles and SES user (the
   operator role is forbidden to do that). Without this step `terraform apply` fails on the new permissions.
2. `AWS_PROFILE=wartide scripts/aws-bootstrap.sh state-bucket` (TLS-only policy, BucketOwnerEnforced, lifecycle).
3. Set `alert_email` (and a real `alert_phone`) in `infra/terraform/terraform.tfvars`, make sure `github_oidc_subjects`
   lists both the `main` and the `environment:production` subjects (see `terraform.tfvars.example`), then
   `terraform init` (commit `.terraform.lock.hcl` if it changed), `terraform plan`, review, `terraform apply`.
   Expect: three security groups replaced (create-before-destroy; the ECS service and RDS are re-pointed, a
   rolling ECS restart), the deploy role trust and the three roles/user updated, the SES user policy narrowed, the ALB
   updated (logs, header dropping, deletion protection), RDS modified in place, plus all `guardrails.tf` resources.
   If GuardDuty is already enabled in the account, `apply` fails with a duplicate detector error: import it with
   `terraform import aws_guardduty_detector.main $(aws guardduty list-detectors --query 'DetectorIds[0]' --output text)`.
   The same applies to an existing account-level S3 public access block (`terraform import aws_s3_account_public_access_block.main <account-id>`).
   Cost anomaly monitor: AWS allows one DIMENSIONAL (per-service) monitor per account and often pre-creates
   `Default-Services-Monitor`; `CreateAnomalyMonitor` then fails with "Limit exceeded on dimensional spend monitor
   creation". Set `anomaly_monitor_arn` in tfvars to the ARN from `aws ce get-anomaly-monitors` and re-run plan/apply
   (the subscription attaches to that monitor; nothing else changes).
4. Click the confirmation link in the email AWS SNS sends to `alert_email` (topic `wartide-prod-alerts`); until then no
   alarm or anomaly mail is delivered. The AWS Budgets emails need no confirmation.
5. GitHub (done by the repo owner, not Terraform): create the `production` environment
   (`gh api -X PUT repos/chaumurky-dev/ww2-game/environments/production`) and move the deploy job into it
   (`environment: production`), after step 3 added its OIDC subject to the trust policy.

## 4. Day-2 operations

- Rotate `SESSION_SECRET` (invalidates all sessions): `terraform taint random_password.session`
 , then `terraform apply`, then
  force a new deployment: `aws ecs update-service --cluster <ecs_cluster> --service <ecs_service> --force-new-deployment`.
- Rotate the SES SMTP key: `terraform taint aws_iam_access_key.ses_smtp`,
  `terraform apply`, force a new ECS deployment as above.
- Scale: `task_cpu`, `task_memory`, `desired_count`, `use_fargate_spot` in `terraform.tfvars`, then apply.
- Mail not arriving: `aws logs tail /ecs/wartide-prod --since 1h | grep email` shows the SMTP error; `aws sesv2 get-account`
  shows sandbox/production and quota; `aws sesv2 list-suppressed-destinations` lists bounced addresses. SES on 587 needs
  `SMTP_TLS=starttls` (the server default; `none` is only for Mailpit). Test without a real inbox by registering
  `success@simulator.amazonses.com`.
- Posture: Fargate Spot (about 70% cheaper; reclaim means a brief outage and dropped WebSockets), 0.25 vCPU / 512 MB,
  no NAT, ALB access logs to S3 (30 days), log retention 7 days, ECR keeps 5 images, scan on push. RDS `db.t4g.micro`,
  gp3 20 GB, single AZ, 7 days of backups, deletion protection on, final snapshot on destroy, `prevent_destroy`.
- Harden RDS further: the safe settings are already the defaults (`db_deletion_protection = true`,
  `db_skip_final_snapshot = false`, `db_backup_retention_days = 7`). Optional extras in `terraform.tfvars`:
  `db_multi_az = true` (doubles RDS cost), `use_fargate_spot = false`.
- Destroy (deliberately takes several steps): (1) in `terraform.tfvars` set `db_deletion_protection = false`
  (and `db_skip_final_snapshot = true` only if you do not want a final snapshot) and `terraform apply`; (2) delete the
  `lifecycle { prevent_destroy = true }` block of `aws_db_instance.main` in `main.tf`; (3) set
  `enable_deletion_protection = false` on `aws_lb.main` and apply; (4) empty the ECR repo if Terraform refuses;
  (5) `AWS_PROFILE=wartide terraform destroy`. The state bucket and IAM role are outside Terraform; remove them
  manually if wanted. GuardDuty, the budget and the account contacts are destroyed with everything else.
- Alerts: budget mail (50% / 100% actual, 100% forecast of `monthly_budget_usd`), cost anomalies of 10 USD or more
  (via the SNS topic), and CloudWatch alarms for log ingest over 200 MB/hour and over 50000 ALB requests per 5 minutes
  all go to `alert_email`. GuardDuty findings are viewable in the console (not mailed; add an EventBridge rule if wanted).

## 5. CI/CD flow

`main` is protected (bootstrap step 12): a change gets there only through a pull request whose CI checks
(`lint`, `test`, `web-build`) passed on an up-to-date branch. Day-to-day flow, hands-off for the reviewer:

```sh
git switch -c <topic> && git commit ... && git push -u origin <topic>
gh pr create --fill && gh pr merge --squash --auto   # merges itself when CI is green; branch auto-deletes
```

A docs-only PR still runs CI (the checks are required, so there is no paths filter). Merging to `main` runs
CI again on the merge commit and, when green, the Deploy workflow.

- `ci.yml` (push/PR): rustfmt, clippy (native + wasm32 for web), `cargo test --workspace` against a Postgres
  service container, trunk release build.
- `deploy.yml`: triggered by `workflow_run` when CI succeeds on `main` (or manually via workflow_dispatch). It
  checks out the CI-validated SHA, builds and pushes `:<sha>` and `:latest` with buildx (GHA cache), fetches the
  current task definition, swaps the image, and deploys waiting for service stability. The ECS circuit breaker
  rolls back failed deploys. Terraform ignores task definition and desired-count drift so it does not fight CI.
- Database migrations run at server startup.
